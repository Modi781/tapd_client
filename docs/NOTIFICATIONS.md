# 新缺陷通知（M6）

通知完全由客户端自绘窗口实现，不使用 macOS 系统通知。轮询、分类、去重与处理动作都在桌面客户端内完成。

## 1. 通知范围

设置 → 新缺陷通知：

| 设置 | 说明 |
| --- | --- |
| 总开关 | 关闭后停止弹窗，但仍可保留轮询状态 |
| 范围 | `我的`（只通知处理人是我）或 `项目`（项目内所有新缺陷） |
| 纯新建 | 新创建且进入范围的缺陷 |
| 转移过来的 | 不是新建，但处理人变成我（优先依据 `assigned_time` 与 `created` 差异；字段缺失时保守判断） |
| 重新打开 | 状态从其它值变为“重新打开” |
| 轮询间隔 | 默认 60 秒，范围 20–600 秒 |
| 免打扰 | 例如 22:00–09:00，期间只累计不弹窗 |
| 最大展示数 | 同时展示的卡片数，默认 3 |

首次启动或重置后，第一轮只建立 baseline，不会把历史缺陷一次性弹出来。

当前轮询只覆盖“上次选择的项目”（`lastWorkspaceId`），避免对全部项目高频请求。

## 2. 通知窗口

- 位置：主窗口所在屏幕右下角，400px 宽，额外卡片向上扩展。
- 无边框、置顶、不占 Dock，深色实底卡片。
- 每条包含：项目、严重程度/优先级、标题、创建人、时间。
- 三个按钮：
  - **处理**：见下一节。
  - **查看**：聚焦主窗口并打开该缺陷详情（通过 `notification://open-bug`）。
  - **忽略**：标记 ignored，同一缺陷后续不再提示；若之后重新打开可再次通知。

设置页提供「模拟通知」，可在不等待真实新 bug 的情况下验收窗口与按钮（模拟项不能执行处理）。

## 3. 处理动作

点击「处理」后，客户端会：

1. 读取当前登录用户（缺失时从 TAPD 获取并写回配置）。
2. 拉取缺陷详情，确认当前处理人与状态。
3. 若处理人不是我，调用 TAPD 内部接口改派：
   `POST /api/entity/bugs/inline_update`，字段 `current_owner`。
4. 若状态是起始状态（`new` / `open` / `reopened`），流转到处理中：
   - 目标依次尝试 `in_progress`、`progressing`（不同项目状态 key 不同）。
   - 首选 `POST /api/aggregation/kanban_aggregation/transition`，失败回退 `POST /api/entity/workflow/transition`。
   - 已是处理中或更后状态时不回退，只改派。
5. 全部成功后标记 handled，并：
   - 触发 M7 入队事件 `agent://enqueue`；
   - 刷新主界面缺陷列表；
   - 更新通知窗口。

任一写入失败时不会标记 handled，也不会入队，通知保持可重试；界面会显示失败原因。改派成功但流转失败时，重试会跳过改派、只重试流转。

> 写接口使用的是网页会话 Cookie + `dsc-token`，与 TAPD 网页端同一权限。客户端不会绕过权限。

## 4. 持久化与重置

- 文件：`~/Library/Application Support/com.tapdclient.desktop/notifications.json`
- 内容：设置、通知历史、seen 去重、ignored、每个项目的轮询游标、baseline 标记。
- 删除该文件可重置 baseline 与历史；下次启动会重新建立 baseline，不会触发历史通知。

## 5. 已知限制

- `assigned_time` 依赖 TAPD 列表/详情返回；若项目不返回该字段，“转移”判定会保守，可能漏报或归类为新建。
- 项目范围会对首次出现的候选缺陷额外拉一次详情，请求量高于“我的”范围。
- 通知窗口不支持拖拽排序/分组；一次最多展示 `maxVisible` 条，其余保留 pending。
- 处理动作只做“改派 + 接受”两步；需要补充其它字段的强制流转会被 TAPD 拒绝并显示错误。
